## Skill proposal and reminder protocol — 2026-10-07

- A useful reusable finding must become a semantic proposal, such as `code-review.md`, outside the active Skill catalog. Do not use numeric, timestamp, UUID or hash basenames. State purpose, trigger/non-trigger, actual evidence, expected benefit, limitations and implementation needs; do not fabricate supporting tasks.
- Both controllers must tell the user in the same active session after the proposal file is written and read back. Include the name, purpose, trigger, evidence qualification, expected benefit, limitations, path and proposed/not-active status. Use one notice per proposal revision per session; preserve deferred and rejected decisions.
- Native final responses append current notices and record inclusion only after conversation persistence. An external `SKILL PROPOSAL REMINDER` capsule MUST be relayed to the user in the current task answer. Tool exposure is not message delivery, and inclusion does not prove that the user read it.
- Use existing `skills` proposal/status/WHY surfaces only when they are actually exposed. A stale connector does not authorize direct catalog writes or a false claim that a proposal was delivered or activated.
- User decisions are approve, revise, reject or defer. Bind decisions to the exact proposal revision and build versus build-and-activate scope. Silence and model-declared consent are not approval. The Native host accepts `/skill build code-review <revision>` or `/skill approve and activate code-review <revision>` from an actual persisted user message. Native user-message provenance remains separate from the explicitly delegated controller path below; never fabricate either source.
- **Trusted proposal controllers — explicit user decision 2026-10-28:** the operator may allow an authenticated controller credential for Skill proposal approval in a registered workspace through `FileKeyStore.setSkillProposalApprover`. The existing auth owner stores `proposal-approvers.json` alongside its key store; no proposal MCP action provisions its own allowance. This Codex connection is authorized by the user for `agent-core`; use the verified credential ID, not a claimed model/product/client name. Everyone holding the same credential shares its allowance. Rotation does not transfer it automatically.
- An allowlisted external controller may use `skills(action=decide_proposal, decision=approve, decisionScope=build|build-and-activate, proposalId=<exact id>, proposalDigest=<exact revision>, confirmation=APPROVE_SKILL_PROPOSAL)` without `userEvidenceRef`. The server must bind authenticated principal, current task and registered workspace, check live allowance/key validity/tool membership, and persist a deterministic `controller-decision:` reference with controller/session/task identity. REJECT/defer/revise on the current revision remains controlling; stale revision, validation and active-catalog drift still stop the operation. Controllers without this allowance retain the existing actual-Native-user-proof route. This delegation grants no other tools, artifact permits or general authentication bypass, and does not turn activation into measured benefit.
- Approval creates a native `SKILL.md` artifact through existing validation/revision/rollback owners, not a new runtime or tool permission. Legacy active Skills are not reclassified or retired by this feature.
- Use `self_awareness` for observed catalog/proposal/Memory/Learning state and `explain_improvement` for the recorded evidence chain. Missing provider, delivery, usage or evaluation evidence stays unknown; proposal qualification and source hashes are not measured intelligence improvement.
- Verified negative Skill use may create a revision proposal through existing Learning state. It never automatically replaces or deletes the active Skill. Failure to write a proposal or notification must not hide an otherwise completed task.
