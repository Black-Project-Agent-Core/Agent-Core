### F-001 A leftover transaction directory without journal.json permanently blocks Memory recovery
- Location: `src/memory/transaction.ts:132` | Unit: memory-3 | Severity/confidence: high/high
- Scenario: commit() creates `state/transactions/<uuid>/` in its first writeOwnedFileAtomic(journalPath), which sits outside the try block. If it throws after mkdir (ENOSPC on open, or EPERM/EBUSY on rename after retries), the empty directory stays. The same happens when the best-effort rm(dir) after a successful commit (line 164) is interrupted on Windows by EBUSY, because it deletes journal.json before it reaches a locked stage file. The next recover() finds a directory with no journal.json, validate() throws ENOENT, and recover() rethrows MEMORY_TRANSACTION_RECOVERY_BLOCKED. Every later snapshot(), commitPlan() and experienceEnabled() runs recover() first, so Memory stays down until someone deletes the directory by hand. MemoryService.initialize turns that error into canonicalStatus 'error'.
- Evidence: transaction.ts:132 writes the journal before the try at 133, so there is no catch to clean up. atomic-file.ts:57 runs mkdir before open and rename, and its finally removes only the temp file. Line 157 catch: validate(dir) returns null when the journal is missing, so rm at 160 is skipped. Line 164 swallows rm failures. Lines 101-104: recover() validates every entry under transactions/. Line 77: readFile(journalPath) throws ENOENT. Lines 113-115 wrap it as MEMORY_TRANSACTION_RECOVERY_BLOCKED. A directory with no journal.json cannot hold an applied mutation, because the journal reaches 'applying' before any target is written.
- Suggested fix: In recover(), treat a transaction directory whose journal.json is absent (ENOENT) as an abandoned preparing directory and rm it. In commit(), move the first journal write inside the try, or rm the directory when that write fails.
- Votes:
  1. confirmed: no guard or caller contract prevents it and no test covers it; callers store.ts:79, 111, 148, 157, 318 all run recover() first; empty journal-less dir blocks recovery (code trace).
  2. confirmed: probe on compiled dist/memory/transaction.js with an empty transactions/<uuid>/ dir made recover() throw MEMORY_TRANSACTION_RECOVERY_BLOCKED (cause ENOENT) and left the dir on disk; the failure injection (ENOSPC/EBUSY) itself was simulated, not injected.
