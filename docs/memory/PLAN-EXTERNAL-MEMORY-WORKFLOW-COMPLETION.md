Setelah izin integrasi terpisah, rekonsiliasi `docs/CODEBASE.md` dua seksi, `docs/research/candidate-source-review-216-20261012.json` entry #18 serta local #134, dan pertahankan `src/skills/service.ts` serta dua file bukti Batch17.

### P1 — Respons tool memberi langkah berikut dan kewajiban task yang benar

- **Masalah/bukti:** `ExternalControllerLearningService.bootstrapInstructions` (`src/learning/external-controller.ts:839–863`) hanya memberi instruksi umum dan hitungan pending; `status` (:1667–1684) mengembalikan total, bukan next step untuk current bound task. `controller_learning(episode,status)` saat ini mengembalikan `current/recent` (controller-learning-tools.ts:63–105); `memory_v2_read(task_context)` sudah memberi continuity/needsCheckpoint (`memory/controller-session.ts:326–340`), dan `learning.checkpoint` sudah mengembalikan `reviewDue/pendingReview` (`learning/service.ts:393–432`).
- **Perubahan minimal yang direncanakan:** tambahkan proyeksi **advisory dan non-authoritative** `workflowNext`/`pendingTaskActions` pada *respons existing* `controller_learning(episode,status/context)` atau pengingat terikat di `src/mcp/external-controller-tool-support.ts::appendSkillReminderCapsule` (jangan ganti pengingat Skill atau membuat tool baru). Sumber hanya current host-bound episode, `terminalOutcome`, `verificationStatus`, `checkpointKeys`, `pendingLearning` dan hasil Learning checkpoint yang sudah ada. Urutan guidance: bind task → recall opsional → nilai penggunaan bila benar-benar menggunakan Memory → verifikasi bila ada bukti → checkpoint → keyed review. Sediakan contoh **nama tool/action yang sekarang valid**, bukan contoh taskId buatan.
- **Keamanan/batas:** proyeksi only-current-scope; tidak bocorkan pending tasks milik owner lain atau user content; unbound/stale menampilkan `scope-unavailable` dan instruksi bind, bukan detail. Jangan membuat kewajiban "receipt untuk semua hit": tidak semua Memory yang dikirim dianggap dipakai. Jika tool response sudah diberi guidance yang cukup setelah implementasi, berhenti; jangan membuat state machine/persistent pending tracker.
- **Kriteria selesai nanti:** caller mendapatkan action berikut dan field yang diperlukan saat task baru, setelah recall, setelah verified/unavailable outcome, saat checkpoint pending, dan setelah `no-new-knowledge`; duplicate read tidak membuat event/use baru; output fail-soft saat Learning status unavailable dan tak mengubah task. **Dependensi:** P0 hanya jika implementasi di branch gabungan; dapat dibuat sebelum P2. **Kontrak/ZIP:** pertahankan nama dan inputSchema tool; tambahan field output opsional/backward-compatible, tanpa ZIP jika descriptor tak berubah. Deskripsi tool bila diubah harus dicocokkan manifest budget.

### P2 — Samakan identitas delivery pada recall v2 dan receipt eksternal

- **Masalah/bukti source yang spesifik:** `ControllerMemorySession.recall` (`src/memory/controller-session.ts:125–225`) menerbitkan `MemoryHit{id,revision,retrievalEvidence:{attemptId,contentDigest,recordFingerprint}}` dan mengisi **ledger canonical exposure** (:101–123). Namun `registerMemoryExperienceTools` (`src/memory/mcp/experience-tools.ts:27–54`) memanggil dispatcher tanpa callback `ExternalControllerLearningService.recordMemoryRecall`. Sebaliknya `memory_search` mencatat delivery ke episode (`src/memory/mcp/tools.ts:188–208`), `controller_learning(context)` biasa melalui `recordMemoryRecall` (:698–716,1214), dan planned context menyimpan `deliveredMemories[attemptId+':'+memoryId]=contentDigest` (:1283–1301). `artifactReceipt` (:1427–1432) mensyaratkan peta episode ini. Jadi **langsung v2 recall → external artifact_receipt** berpotensi menghasilkan `EXTERNAL_RECEIPT_MEMORY_NOT_DELIVERED_TO_TASK` meski ledger punya returned-to-controller. Ini inferensi dari wiring source, **bukan** kegagalan live yang baru dites.
- **Perubahan minimal yang direncanakan:** di `src/memory/mcp/experience-tools.ts::registerMemoryExperienceTools` dan `src/mcp/server.ts`, hubungkan hasil `memory_v2_read(action=recall)` yang **betul-betul dikirim** ke observer external existing. Jika signature internal diperlukan, tambahkan adapter internal ringan di `src/learning/external-controller.ts` yang memanggil logika `recordMemoryRecall` yang sama untuk tuple valid `{taskId,attemptId,memoryId,contentDigest}`; **jangan** membuat ledger, mirror persistence alternatif, atau writer receipt baru. Reuse `currentExternalInvocationContext`/`invocationDisclosureCurrent` dan resolver `src/memory/mcp/scope.ts`. Peta episode hanya diisi untuk hit yang admitted dan returned-to-controller setelah budget; bukan dropped/omitted/insufficient-budget, dan hanya bila task+owner+workspace+head masih cocok.
- **Error handling:** timeout/cancellation/late-settlement atau perubahan task tidak boleh membuat "delivered" palsu. Jika canonical ledger sudah tercatat tetapi mirror episode gagal, status penyelarasan dilaporkan `unavailable`/advisory; jangan mengklaim receipt eligible, jangan mengulang recall otomatis demi mengarang attempt baru. Ledger authoritative; original source/digest tetap utuh. Replay duplicate attempt + same digest idempotent, conflict/rotation ditolak.
- **Kriteria selesai nanti:** satu host-bound task dengan direct v2 recall yang returned-to-controller dapat membuat receipt melalui `controller_learning(artifact_receipt)` untuk exact attempt+memory+digest; wrong task/owner/workspace, dropped hit, stale digest, duplicate conflict dan late result tetap ditolak; ordinary/planned context tidak regress. **Dependensi:** P1 membantu caller, namun mekanisme P2 independen; P0 bila branch target gabungan. **Kontrak/ZIP:** parameter tool `memory_v2_read` tidak berubah; cukup wiring internal/response advisory kompatibel, maka ZIP tidak dibutuhkan tanpa perubahan manifest publik.

### P3 — Keputusan pemakaian, outcome dan feedback berbasis evidence yang tersedia

- **Masalah/bukti:** di `src/learning/external-controller.ts::artifactReceipt` (:1406–1457), receipt memory sekarang memvalidasi `deliveredMemories`, menggunakan `LearningService.receipt` → `MemoryService.recordUseReceipt` (`memory/service.ts:600–635`) → `MemoryRetrievalLedger.recordUseReceipt` (`memory/retrieval-ledger.ts:376–448`). `validateWorkflowUse` (`src/learning/workflow-evidence.ts:78–95`) membedakan controller-reported dan independently checked result; fallback `result=unavailable` sudah ada. Namun awal `artifactReceipt` mengambil `getEpisode(sessionId)` dan membandingkan caller `taskId` hanya jika diberikan, tanpa eksplisit memverifikasi host-issued invocation `owner/task/current-head` setara `verifyEpisode` (:759–807). Alternatif `learning(action=receipt)` (`src/mcp/learning-tools.ts:76–92`) juga meneruskan input ke Memory secara langsung. Penggunaan mekanisme ini pada setiap AI external **belum terbukti**.
- **Perubahan yang direncanakan:** dahulukan kontrak guidance P1 dan binding P2; bila source gate belum menjamin exact caller saat penggunaan, pakai **validasi host-issued scope existing** di entrypoint receipt external dan, untuk jalur `learning(receipt)`, terapkan pemeriksaan sepadan hanya saat caller external host-bound. Jangan mengganti `validateWorkflowUse`, ledger idempotence atau `MemoryService.feedback`; jangan membebankan pembatas external pada Native yang punya task identity sendiri. `reasonCode` mencerminkan alasan caller `applied/adapted/rejected`, bukan classification otomatis.
- **Aturan outcome:** caller menyatakan tindakan yang benar-benar dipengaruhi, menyertakan `actionRefs` yang valid + exact `retrievalAttemptId,memoryId,contentDigest`, dan `verificationRef` hanya bila ada. Result `success/failure` tervalidasi hanya bila verifier menghasilkan resolved/pasangan verdict; jika bukti tak lengkap simpan `reportedResult` tetapi verified `result=unavailable`. `rejected` boleh dengan reason yang nyata dan status unavailable; `stale-content` memakai aturan existing; tidak menganggap setiap rejection sebagai wrong Memory. `verifyEpisode` B16 tetap bagian **task outcome** terpisah dan tidak otomatis membuat Memory receipt.
- **Aturan feedback:** hanya ketika caller secara eksplisit memilih `memoryFeedback=helpful/not-helpful` untuk receipt applied/adapted dengan evidence resolved dan digest cocok, gunakan `memory.feedback` existing. Penggunaan `memory_feedback(kind=stale/wrong)` memerlukan alasan/bukti independen; jangan tulis feedback karena task sukses/gagal atau sekadar banyak recall. Simpan event idempotent per task+memory+digest; kegagalan feedback sesudah receipt ditampilkan `unavailable` tanpa rollback receipt. Tidak ada formula ranking/retention baru.
- **Kriteria selesai nanti:** tiga keputusan penggunaan nyata dapat dicatat dan direplay tanpa inflasi duplikat; id/digest/task mismatch tertolak; negative/unknown outcome tidak salah diberi kredit; true verified use dapat memicu satu feedback yang memang diminta; direct v2 dan planned path memakai writer yang sama. **Dependensi:** P2 untuk direct v2, P1 untuk compliance. **Kontrak/ZIP:** tool `controller_learning(artifact_receipt)` dan `learning(receipt)` sudah punya field yang dibutuhkan; tidak perlu field baru. Jika existing input schema cukup, ZIP tidak diperlukan.

### P4 — Finalisasi checkpoint secara task-scoped, tanpa menutup backlog historis

- **Masalah/bukti:** `learning(action=checkpoint)` pada `src/mcp/learning-tools.ts:48–65` menerima `taskId` opsional dan memanggil `ExternalControllerLearningService.recordLearningCheckpoint`, tetapi mengabaikan error mirror dengan `catch(() => undefined)`. `learning(action=review)` (:66–76) juga mengabaikan kegagalan mirror. `LearningService.checkpoint` (`src/learning/service.ts:393–432`) sudah menghasilkan `reviewDue` dan `pendingReview`; `review` (:464–578) mempunyai exact `checkpointKeys`, `taskId` mismatch guard, `disposition` dan idempotence; `markReviewed` (`src/learning/triggers.ts:92–105`) menghapus hanya key yang complete. 24 pending pada snapshot awal adalah sejarah, bukan alasan mengeksekusi mass close. Tidak ada scheduler yang otomatis menjalankan review setiap `reviewInterval=10`.
- **Perubahan yang direncanakan:** pada external MCP branch `src/mcp/learning-tools.ts::registerLearningTools`, gunakan `currentExternalInvocationContext` dan `resolveTaskScope` yang sudah dipakai oleh `learning(action=decision)` untuk memvalidasi host-issued task dan workspace sebelum membuat **checkpoint baru pada task bound**, serta sebelum keyed review yang mengaku menutup task itu. Native/non-host yang sah tetap memakai jalurnya. Setelah Learning store berhasil commit, pertahankan fail-soft mirror ke `ExternalControllerLearningService.recordLearningCheckpoint/recordLearningReview`; tampilkan keterbatasan sinkronisasi bila mirror gagal, bukan menyatakan kedua state pasti identik. Jangan rollback Learning yang sudah durable atau menghasilkan event duplikat untuk menyembunyikan mismatch.
- **Respons guidance:** return `checkpointKey` dan pemanggilan `learning(review,checkpointKeys:[key],taskId,disposition:'no-new-knowledge'|'awaiting-verification'|'rejected',candidates:[])` bila tidak ada kandidat. `no-new-knowledge` memenuhi finalisasi; penolakan kandidat tidak sama dengan kegagalan task. `awaiting-verification` harus tercatat sebagai keputusan eksplisit dan tidak disulap menjadi kandidat verified. Setelah keyed review berhasil, status episode `pendingLearning=false` bila seluruh key episode complete; jangan menghapus pending milik tugas lain. Task terminal tetap ditentukan oleh `verifyEpisode`, bukan oleh review.
- **Kriteria selesai nanti:** new external checkpoint yang benar terikat exact host task dan terlacak sampai scoped review; taskId kosong/foreign/stale tidak menghasilkan checkpoint misleading; duplicate idempotencyKey tidak menggandakan review; mirror failure ditampilkan sebagai `linkage-unavailable`; legacy taskless historical pendings tidak dimodifikasi atau diberikan taskId tebakan. **Dependensi:** P1; P3 tidak wajib bila task tidak memakai Memory. **Kontrak/ZIP:** existing `learning` action/input sudah cukup; usahakan respons compatible dan no new ZIP.

### P5 — Buka detail dengan SourceRef persis, hanya jika perlu

- **Masalah/bukti:** `src/memory/disclosure.ts:16–72` menetapkan `MemoryHit{id,revision,availableViews,retrievalEvidence}` dan `Budgeted` response. `ControllerMemorySession.expand` (`src/memory/controller-session.ts:227–320`) sudah memeriksa scope, exact revision, archive, cursor dan batas bytes, lalu memberi `partial/insufficient-budget/nextCursor`. `controller_learning(context)` biasa (`src/learning/external-controller.ts:1334–1360`) hanya memproyeksikan `id/title/category/content/retrievalEvidence`, **tanpa SourceRef/revision**; planned `context(retrievalPlan)` sudah menyertakan `hit.revision` dan `origins` dalam `memoryRetrieval` (`src/memory/subquestion-retrieval.ts:63–112`). Kekurangan metadata pada jalur biasa adalah gap output ringan, bukan alasan membuat retriever baru.
- **Perubahan yang direncanakan:** untuk memory **yang benar-benar masuk response** jalur context biasa, sertakan optional `sourceRef:{kind:'memory',id,revision}` yang dihasilkan dari `memorySemanticRevision(record)` di owner `src/memory/disclosure.ts` dan pemanggil `external-controller.ts::contextCore`. Jangan menebak revisi dari timestamp maupun membaca `memory_read` sebagai substitusi exact expansion; bentuk proyeksi harus mengikuti versi Memory actual. Jalur planned/v2 yang sudah mengirim revision dipertahankan. Tidak menambah view/tool baru.
- **Keputusan caller dan stop condition:** baca abstract lebih dahulu. Expand `view:'record'` dengan SourceRef exact **hanya** jika keputusan masih kurang bukti, berkonflik, atau ada pengecualian penting; view `'evidence'`/`'episode'` hanya untuk SourceRef berjenis tepat dan `availableViews` yang benar. Pada partial, gunakan `nextCursor` hanya untuk **request identik** dan revisi sama; berhenti setelah informasi cukup, ketika `status=ok`, source unavailable, cursor stale, scope/retention invalid, budget insufficient atau batas discretionary tercapai.
