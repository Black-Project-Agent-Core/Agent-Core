# Market Signal Lab v0.3 Alpha 6.5.2.1 — Live Scan Telemetry & Adaptive ETA Design

## Status

Approved visual direction. This spec is an operational UX and telemetry upgrade on top of Alpha 6.5.2. It does not change Trends & Insights formulas, consensus formulas, ranking models, Envato source policy, or market-analysis scope.

## Goal

Make every `Map Market Now` run observable and auditable while it is running. The user must be able to distinguish the live run from the last completed market map, understand which stage is active, see factual current-run progress, inspect recent warnings/errors, and receive an ETA that becomes more accurate as real local telemetry accumulates.

## Core principle

Progress is a fact about the **current scan plan**. ETA is an estimate informed by **current-run telemetry plus comparable persisted history**. The previous run's product count must never be used as the progress denominator.

## Approved UI structure

The Market Autopilot page keeps the responsive Alpha 6.5.2 shell and adds a prominent `Live Market Mapping` panel directly below Scope / Scan Mode / Schedule and the Map/Refresh actions.

The live panel contains:

1. running/completed/partial/failed/cancelled status;
2. stage tracker;
3. factual work-unit progress bar;
4. discovered products count;
5. completed work units / planned work units and request count;
6. elapsed time;
7. estimated remaining time;
8. expected finish time;
9. ETA confidence;
10. latest five structured events;
11. `View Full Log` drill-down.

Below the live panel, existing analytical metrics are relabeled as `Last Completed Map` while a new scan is running. They must never visually masquerade as live-run results.

## Stage model

Canonical stages for Alpha 6.5.2.1:

1. `preparing_scan_plan`
2. `validating_sources`
3. `loading_catalog_structure`
4. `mapping_market_surfaces`
5. `normalizing_products`
6. `deduplicating`
7. `taxonomy_segmentation`
8. `signal_quality_audit`
9. `ranking_consensus`
10. `persisting_history`
11. `finalizing_market_map`

Each stage can be `waiting`, `running`, `completed`, `warning`, `failed`, or `skipped`.

## Work-unit progress

`progressPercent = completedWorkUnits / plannedWorkUnits * 100`.

A work unit is a planner-owned bounded unit such as a target surface/category task or a deterministic post-processing stage unit. Work units must be known or derivable from the current plan. If the planner cannot yet establish a denominator, the progress bar is indeterminate and displays `Preparing scan plan…` rather than a fabricated percent.

The following are never valid denominators:

- previous product count;
- expected product count guessed from scan mode;
- Quick/Standard/Deep hard-coded duration;
- arbitrary percentages per stage.

Discovery volume is displayed separately:

- current discovered products;
- current unique products;
- previous comparable-run product count when available;
- delta vs previous comparable run.

## ETA model

ETA is produced by a deterministic `ScanRuntimeEstimator`, not AI.

Inputs:

- remaining planned work units;
- current-run completed work units;
- current elapsed time;
- current moving work-unit duration;
- current request latency (p50/p95 where available);
- retries and retry delay;
- comparable completed runtime histories;
- stage-specific historical durations;
- planner/sampling/source compatibility.

Comparable historical runs are selected from persisted telemetry using structural compatibility, not merely the label Quick/Standard/Deep. Scan mode affects what work is planned, not how long the ETA assumes it will take.

### ETA evidence states

- No historical telemetry and insufficient current progress: `Calibrating…`, confidence `Unavailable`.
- Current-run-only estimate: show a range, e.g. `8–14 min`, confidence `Low`.
- 1–2 comparable historical runs: approximate ETA, confidence `Low`.
- 3–5 comparable historical runs: confidence `Medium`.
- 6+ comparable historical runs: confidence `High`, subject to runtime degradation.

If current latency/retries diverge materially from history, ETA must reweight toward current-run speed and may lengthen or shorten live.

## Structured telemetry event

Every event is normalized. It must not be a raw log dump.

Minimum fields:

- `id`
- `runId`
- `timestamp`
- `stage`
- `severity` (`info`, `warning`, `error`)
- `code`
- `messageKey`
- `sourceSite` optional
- `marketSurface` optional
- `catalog` optional
- `requestNumber` optional
- `latencyMs` optional
- `retryCount` optional
- `retryDelayMs` optional
- `itemsReceived` optional
- `uniqueItems` optional
- `workUnitsCompleted`
- `workUnitsPlanned`

Token values, Authorization headers, cookies, raw HTML, and raw API payloads are forbidden.

## Persisted run telemetry

Completed or terminal runs persist a summary containing:

- started/completed timestamps;
- terminal status;
- planned/completed work units;
- discovered and unique products;
- requests used;
- average, p50, p95 latency;
- retry count and retry delay;
- warning/error counts;
- stage durations;
- site/surface durations where available;
- planner version;
- sampling schema version;
- enabled sources/surfaces;
- compatibility fingerprint.

Detailed structured events are append-only. A bounded recent-event view is used by the main dashboard; full history is available through a modal/drawer and history API.

## Live delivery

Alpha 6.5.2.1 uses a local event stream from the Go server to the browser. Preferred transport is Server-Sent Events because telemetry is server-to-client and does not require bidirectional WebSocket semantics.

Required local endpoints:

- `POST /api/autopilot/run` starts the run and returns the run identity immediately rather than blocking until completion;
- `GET /api/autopilot/live?runId=<id>` returns the current telemetry snapshot;
- `GET /api/autopilot/live/events?runId=<id>` streams new telemetry events via SSE;
- `GET /api/autopilot/run-log?runId=<id>` returns paginated structured historical events;
- `GET /api/autopilot/runtime-history` returns historical runtime summaries used for audit/display.

The server owns telemetry truth. Closing or refreshing the browser must not terminate an already-running server-side scan unless the process itself exits or a future explicit cancel action is invoked.

## Error behavior

Warnings such as `429 Retry-After`, an optional surface failure, or transient connector errors appear in live telemetry and adjust ETA/quality. Recoverable warnings do not automatically terminate the run.

Fatal failures (e.g. invalid auth where no usable source remains) produce a terminal failed stage and preserve the log up to failure.

The UI must never hide an error inside an animation. Terminal status, last error, and failure stage remain visible.

## Live vs completed data separation

While a scan is active:

- `Live Market Mapping` shows current-run telemetry only.
- `Last Completed Map` shows the most recent completed analytical result only.
- Previous values remain visible but explicitly labeled as previous/completed results.
- No current-run partial analytical score is substituted into completed Trend/Opportunity/Consensus results unless the relevant existing engine already publishes a formally finalized snapshot.

## Localization

English remains default/fallback. Indonesia remains the second locale. Every new stage, severity, event code, ETA state, button, label, and error has translation keys with parity tests.

## Responsive behavior

The approved concept is the visual target. At 1366×768 / 100% browser zoom:

- no body horizontal overflow;
- the live panel remains readable;
- recent log shows five entries;
- stage tracker may compress labels but cannot overlap;
- on narrower screens the recent log moves below progress metrics;
- below 900px the stage tracker becomes a vertical or compact step list;
- `View Full Log` uses a responsive modal/drawer.

## Security and privacy

No telemetry field may persist or render:

- Envato token;
- Authorization header;
- cookies;
- browser storage;
- account email;
- raw API body;
- raw HTML.

Existing secret-redaction utilities are applied before event persistence.

## Compatibility

All Alpha 6.5.2 analytical data and Browser Companion data remain compatible. Existing historical runs without runtime telemetry are valid market history but are not treated as runtime-history evidence for ETA.

The first machine/run therefore may show `Calibrating…` until enough factual current-run progress exists.

## Non-goals

Alpha 6.5.2.1 does not add or change:

- AI/LLM/embeddings;
- mock market data;
- Trend/Opportunity formulas;
- Cross-Surface Consensus formulas;
- review/rejection prediction;
- portfolio scoring;
- Market Flow/Cohort Engine;
- Historical Echo/seasonality.

## Acceptance criteria

1. Starting Map Market Now immediately produces a run ID and visible live panel.
2. Progress is derived only from current-run planned/completed work units.
3. Previous product count is never used as progress percent denominator.
4. When no reliable denominator exists, progress is indeterminate rather than fabricated.
5. ETA begins as unavailable/calibrating when evidence is insufficient.
6. ETA updates as current work-unit speed, latency, retry delay, and comparable history change.
7. ETA does not hard-code durations by scan mode.
8. The latest five events are visible on the main page; full structured log is accessible.
9. Recoverable 429/retry events are visible and influence runtime estimates.
10. Fatal errors remain visible with stage/error context.
11. Live run data is visually separated from Last Completed Map metrics.
12. Telemetry survives browser refresh while the server process continues.
13. Runtime summaries and event history are persisted locally and exportable without secrets.
14. English and Indonesia translation parity passes.
15. Responsive QA passes at 1920×1080, 1600×900, 1440×900, 1366×768, 1280×720, 1024×768, and 768×1024.
16. No mock runtime data and no AI dependency are introduced.
